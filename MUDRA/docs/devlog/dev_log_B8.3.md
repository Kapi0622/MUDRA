## 1. 概要

| 項目 | 内容 |
|---|---|
| **出発点** | 敵は `weakElement`（弱点1つ）と `weakMultiplier` を持ち、相性は「弱点 ×1.5 か、それ以外 ×1.0」の2段階。弱点の割り当ては敵ごとに個別で規則が無く、弱点以外では業火がほぼ全敵で最速の万能枠になっていた（dev_log_B8 §技術的負債） |
| **ゴール** | 敵に属性を持たせ、相性の規則から有利・不利を導く。法則を1枚の図で説明できる。将来のオンライン対戦と同じ規則で動く |
| **結果** | 循環 水→火→風→土→雷→水 と 光⇄闇。有利 ×1.5 / 不利 ×0.75（同じ属性も不利）/ 無は常に等倍。**自分の属性（最後に撃った攻撃術）を導入し、敵の攻撃にも相性を掛ける。** HP バーに属性と弱点、HUD 右上に相性図 |
| **変えなかったもの** | 速度ボーナス・コンボ・連続減衰の計算、Stun の確率判定、回復量（相性を乗せない）、効果音（不利では鳴らさない）、セーブの形、術・敵の数値 |
| **進め方** | 変更書の調査 → 質問（4点まとめて）→ 計画承認 → Step 1〜6 を1つずつ提案・承認して実装 |

## 2. 決めた方針（論点と結論）

| 論点 | 結論 | 理由 |
|---|---|---|
| 通常モードの自分の属性 | **オンラインと完全に共通化。** 自分の属性 = 最後に撃った攻撃術の属性。敵の攻撃は敵自身の属性を持つ | 調べると、連続減衰が見ていた `LastAttackElement` がそのまま「最後に使った技の属性」だった。共通化しても状態は増えない。弱点の術を撃つと守りにも効く（水を撃てば火の攻撃が ×0.75）ので、方針が一貫する |
| 相性表の持ち方 | **コードの規則（static class）** | 変更書は SO＋カスタムエディタ＋注入だったが、規則で全マスが決まる。表にすると規則外のマスを作れ、対戦で双方の表が食い違う余地も生まれる。注入が要らないので App 側（ステージ選択・図鑑）からもそのまま呼べる |
| 倍率の置き場所 | `BalanceData.AffinityMultiplier(関係)` | B8 の「調整値は1か所」に合わせる。`ElementAffinity` は関係だけを返し、数値を持たない |
| Calculator の形 | `Calculate(SpellData, float affinity, DamageBonus)`。`EnemyData` を外す | 受ける側を知らない Strategy にしておけば、対戦で受ける側がプレイヤーでも同じものを使える。関係（`Relation`）は `BattleModel` が結果に埋める（`StunResisted` と同じ扱い） |
| `IsWeakness` | `Relation` から読むプロパティに変更 | 参照側（チュートリアル・効果音・戦績・数字）を一切直さずに済む |
| 光と闇 | **互いに弱点**（変更書は光→闇の一方向） | ユーザー判断。感覚的に分かりやすい。倍率は他と同じ（値を増やさない）。ステージ4は「光を撃った直後は闇の攻撃を ×1.5 で受ける」相討ちになる |
| 言葉 | 「弱点！」= 受ける側が苦手、「耐性」= 受ける側が強い。**術の数字にも自分の被弾にも同じ2語** | 向きが変わっても同じ規則だと分かるように。Stun の「抵抗」とは別の言葉にした |
| 戦闘中の表示 | 敵の HP バー「泥人形　土　／　弱点　風」、自分の HP バー「自分の属性　土」、右上に相性図 | 相性図があっても、詠唱中の来場者が矢印を辿らずに次の一手を決められるよう弱点も出す。自分の属性は守りに効くので見えないと理不尽 |
| 相性図の位置 | 右上 170×170px（ボスの HP バー・状態アイコン・コンボの間） | 右下は App 側のカメラ映像、左下は詠唱中の術ガイドが伸びてくる。重なるのは一時的な演出（カットイン・警告の帯）だけ |
| 相性図の作り方 | 文字まで含めた1枚の画像（生成AI） | 当初は「AIは漢字が崩れやすいので文字なしで生成して TMP で重ねる」と提案したが、ユーザーの指摘どおり一括の方が変更が少ない。崩れた時だけ TMP に切り替える予備の手にした。届いた画像は7字・矢印とも正しかった |
| チュートリアル本文 | 指示パネルを 320→384px に広げ、本文を4行に | 欄は 26pt で1行約22字・2行（88px）しかなく、承認した文言は約8行。変更前の文言もすでに4行ではみ出していた。文言を4行に詰め、例の術は1つに絞った |
| テスト | `Editor/Tests/` に EditMode テストを1本 | 自前コードに asmdef が無く、別アセンブリのテストからはゲームのコードを参照できない。Assembly-CSharp-Editor に置けば NUnit も解決できた。期待値は規則から計算せず手で書いた表 |

## 3. 進め方の記録

| Step | 内容 | つまずいた点 |
|---|---|---|
| 1 データとロジック | enum・`BalanceData`・`EnemyData`・`ElementAffinity`・Strategy・`BattleModel`・参照箇所の追従。見た目は変えずにコンパイルを通す | CRLF のファイルが多い（Data・Model 全般）。置換は改行コードを保って行った |
| 2 アセット | 生成ツールの定義表を属性に書き換えて再実行。双刃・回復術を無に | 実行前に、生成が上書きする欄（セクション・行動パターン）が定義表にある欄だけかを確認した。差分は属性の行と、既定値のまま書き出された2欄だけ |
| 3 UI・文言 | 数字のラベル、HP バーの名前欄、図鑑、敗北ヒント、チュートリアル | ①自分の HP バーに名前欄が無かった → ボス側の欄を複製。②区切りの「｜」がフォント（ShipporiMincho の静的アトラス）に無い → 開始演出と同じ「／」に。③**文字の長さを測るのに使った `TMP_Text.GetTextInfo(string)` が、テキストそのものを書き換えていた**（シーンの差分で気づいて元に戻した）。測るだけなら `GetPreferredValues` を使う |
| 4 相性図 | 生成プロンプト（`docs/affinity_chart_asset_prompt.md`）、HUD への配置 | 配置を決める時に Unity が再生中だった。再生中の変更は消えるので、調査だけ先に行い（再生中の方が App 側のカメラ映像の位置まで分かった）、配置は停止後にした |
| 5 テスト | 11件（全64マス・弱点・無・有利がちょうど1つ・倍率） | なし |
| 6 文書 | 下の §6 | 早見表のスクリプトが残っていなかったので作り直した（作業用。リポジトリには置かない） |

## 4. 確認手順（ユーザー側）

キーボードモード（`1`〜`5`=詠唱印 / `U`=合 / `Space`=発動、Calibration は `F2`、Tutorial は `Tab` で飛ばせる）で:

1. 風刃 vs 泥人形で「弱点！」、業火 vs 鬼火で「耐性」、雷連撃 vs 泥人形で表示なし
2. 火炎弾 vs 鬼火で、DoT の tick も小さくなる（33+75 → 24+57）
3. 双刃がどの敵にも等倍で、撃つと自分の属性が「無」になる
4. 水爪の後に鬼火の攻撃を受けると被ダメージに「耐性」、風刃の後なら「弱点！」
5. 敵が替わると自分の属性が「無」に戻る
6. 蟹坊主の弱点が風（ステージ選択・図鑑・敗北ヒント・HP バー）。他の敵の弱点は変更前と同じ
7. チュートリアルの「属性」の段階が達成でき、本文がパネルからはみ出さない
8. 右上の相性図が読める大きさか
9. 全ステージを通しで遊べるか（特にステージ3の水不足、ステージ4の相討ち）

## 5. 技術的負債・保留事項

- **バランスは未調整。** 早見表（`balance_sheet.md` §3）の観点: 光の術（破魔光）が闇以外の全敵に等倍で、次の万能枠になりそう／水蛇では弱点の雷連撃より等倍の氷風の方が速い（5段の切り捨て）／ステージ3は弱点がほぼ水で水の術は1つ／ステージ4は被ダメージが増える方向
- **ランクの被弾の目標値（`rankTargetDamage`）は据え置き。** 相性で被ダメージが変わったので、通しプレイの後に見直す
- （済）図鑑の説明文。`codex_text.md` の岩砕・双刃・回復術を直し（相性と食い違っていたため）、`SpellData.description` にも流し込んだ
- **`BD_Balance.asset` に相性の倍率がまだ書き出されていない。** 読み込み時はコードの既定値（1.5 / 0.75）が入る。Inspector で一度触れば書き出される
- **相性図はハイライトしない。** 今の敵・自分の属性を図の上で光らせる案は、画像1枚の作りでは出来ない（やるなら文字を TMP にする）。HP バーの名前欄で足りるか通しプレイで見る
- **`ElementRelation` の値はシリアライズされていない**が、`ElementType` に合わせて明示値にしてある
